# اسکریپت‌های عملیاتی

این چهار فایل **کپیِ مرجع** اند، نه چیزی که اجرا می‌شود. نسخه‌ی زنده
جای دیگری است و `deploy.sh` هیچ‌کدام را نمی‌فرستد:

| فایل | جای واقعی | اجرا |
|---|---|---|
| `backup.sh` | `root@130.185.72.87:/opt/billiardhub/backup.sh` | کران، ۳:۰۰ |
| `disk-guard.sh` | `root@130.185.72.87:/opt/billiardhub/disk-guard.sh` | کران، هر ساعت |
| `pull-from-server.sh` | لپ‌تاپ: `I:/BilliardhubBackup/` | Scheduled Task، ۴:۰۰ |
| `prune-build-cache.ps1` | لپ‌تاپ: `%LOCALAPPDATA%\billiardhub\` | Scheduled Task `BilliardHub-PruneBuildCache`، ۲:۳۰ |

## چرا این‌جا کپی شده‌اند

تا دیروز هیچ‌کدام در هیچ ریپویی نبودند. یعنی اگر لپ‌تاپ یا سرور از
دست می‌رفت، خودِ سازوکارِ پشتیبان هم می‌رفت — و تاریخچه‌ی تغییرش هیچ‌جا
نبود.

**پس از هر تغییر روی سرور، کپی این‌جا هم به‌روز شود.** برای همین
`ops/` عمداً بیرونِ `apps/` است: بخشی از اپلیکیشن نیست.

⚠️ و برعکسش هم مهم است: هیچ‌کدامِ این‌ها نباید **از داخلِ ریپو**
اجرا شوند. `prune-build-cache.ps1` اولش همین‌طور بود و Task مستقیم
به `ops/` اشاره می‌کرد — یعنی یک `git checkout` روی شاخه‌ای که این
فایل را ندارد، یا یک `git clean -xdf`، بی‌صدا اسکریپتی را حذف
می‌کرد که ساعت ۲:۳۰ بدونِ نظارت فایل پاک می‌کند. نصب/به‌روزرسانیِ
نسخه‌ی زنده‌اش:

```powershell
& "ops\prune-build-cache.ps1" -Install -Root "I:\Billiard Plus\billiard-plus"
```

## هرسِ کشِ بیلد — چرا لازم شد

پوشه‌ی پروژه روی لپ‌تاپ ۸۹ گیگابایت شده بود. اندازه‌گیری: ۸۶ گیگش
`.turbo/cache` بود — ۱۲۶۳ ورودی انباشته از تیرماه، به‌علاوه‌ی ۳
فایلِ `.tmp` نیمه‌کاره‌ی ۱٫۳ گیگی. **Turborepo کشش را هرگز خودش
پاک نمی‌کند**؛ نه سقفِ حجم دارد نه سقفِ سن.

پس از پاک‌سازی: **۸۹ گیگ → ۱٫۶ گیگ**. اسکریپت روزانه سه قاعده را
اعمال می‌کند (نیمه‌کاره‌ها، کهنه‌تر از ۷ روز، و سقفِ ۱۰ گیگ برای هر
پوشه) و اگر حذفی شکست بخورد با کدِ ناصفر تمام می‌شود تا Task
«موفق»ِ دروغین گزارش ندهد. لاگ: `%LOCALAPPDATA%\billiardhub\prune-cache.log`

## نکته‌ی مهمِ پشتیبان

`backup.sh` دیگر هر شب `tar` کامل نمی‌گیرد. حالا:

```
/var/backups/billiardhub/
  <stamp>/            دامپِ دیتابیس + کانفیگ + media.sha256   (~۶۵۰ کیلوبایت)
  media/current/      آینه‌ی rsync از فایل‌های Storage
  media/<stamp>/      عکسِ لحظه‌ای با هاردلینک (تقریباً رایگان)
  media/index         path|size|mtime|sha256
```

بازیابیِ فایل‌ها یعنی کپی از `media/current` یا از عکسِ همان تاریخ.
بازیابیِ دیتابیس: `pg_restore` روی `public.dump`.
