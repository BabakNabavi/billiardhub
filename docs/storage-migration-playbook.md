# مهاجرتِ Storage — دفترچه‌ی آماده

> این سند **دستورِ اجرا نیست.** نقشه‌ای است برای روزی که پهنای‌باند
> گران شود. تا آن روز هیچ‌کدام از این کارها لازم نیست.

## کِی؟ — تریگرِ عددی

مهاجرت کن وقتی **egressِ ماهانه از حدودِ ۲ تا ۳ ترابایت گذشت**.

| مقیاس | Supabase نگهداری | Supabase egress | R2 نگهداری | R2 egress |
|---|---|---|---|---|
| ۵۰۰ GB | ~$۸٫۵ | بسته به تماشا | ~$۷٫۵ | رایگان |
| ۱ TB | ~$۲۰ | بسته به تماشا | ~$۱۵ | رایگان |
| ۵ TB | ~$۱۰۷ | بسته به تماشا | ~$۷۷ | رایگان |

*(نرخ‌ها از صفحه‌ی رسمیِ هر سرویس، مرداد ۱۴۰۵: Supabase Pro
۱۰۰ GB نگهداری و ۲۵۰ GB egress شامل، سپس $۰٫۰۲۱۳/GB و $۰٫۰۳/GB.
Cloudflare R2: $۰٫۰۱۵/GB-ماه، egress رایگان.)*

**تفاوتِ نگهداری ناچیز است.** آنچه مهاجرت را توجیه می‌کند فقط
پهنای‌باند است — یک ویدیوی ۲۰ مگابایتی که هزار بار دیده شود ۲۰
گیگابایت egress می‌خورد، بیشتر از هزینه‌ی سالانه‌ی نگهداری‌اش.

## وضعیتِ آمادگی — چه چیزی آماده است، چه چیزی نه

### ✅ ویدیو — آماده

`videos` کلیدِ فایل را جدا از نشانی نگه می‌دارد:

```
storage_provider   'supabase'
storage_key        social/media/vid/<id>.mp4
thumb_key          social/media/thumb/<id>.jpg
src / thumb        نشانیِ کامل — فقط تکیه‌گاهِ ردیف‌های قدیمی
```

نشانی همه‌جا از کلید ساخته می‌شود: فهرست، صفحه‌ی تماشا، `VideoObject`،
Open Graph و نقشه‌ی سایتِ ویدیو. یعنی **تغییرِ ارائه‌دهنده هیچ‌کدام را
نمی‌شکند.**

### ⚠️ تصویر — عمداً آماده نشده

عکسِ باشگاه، محصول، پروفایل، فروشگاه و استوری همچنان **نشانیِ کامل**
را در دیتابیس دارند.

**چرا عمداً:** همه‌ی این نشانی‌ها *دقیقاً یک پیشوند* دارند، پس مهاجرتشان
یک `UPDATE` ساده است (پایین). ساختنِ ستونِ کلید برای پنج جدول و
به‌روزکردنِ همه‌ی مسیرها، کارِ امروز را زیاد می‌کند تا کارِ آن روز کمی
کمتر شود — معامله‌ی بدی است.

ویدیو استثنا شد چون نشانی‌اش در داده‌ی ساختاریافته و نقشه‌ی سایت هم
می‌نشیند، جایی که کهنگی هزینه‌ی سئو دارد.

## چه چیزی باید عوض شود

### ۱) کد — سه فایل

| فایل | تغییر |
|---|---|
| `lib/supabase-config.ts` | افزودنِ ریشه‌ی ارائه‌دهنده‌ی تازه |
| `lib/media/storage.ts` | یک `case` تازه در `publicUrlFor` |
| `next.config.js` | افزودنِ دامنه‌ی تازه به `img-src` و `media-src` |

`lib/media/storage.ts` عمداً یک تابع است نه یک لایه‌ی کلاسی: با یک
ارائه‌دهنده، انتزاعِ بیشتر فقط یک لایه بینِ کد و کاری است که درست کار
می‌کند. اگر ارائه‌دهنده‌ی دوم واقعاً آمد، **آن لحظه** جای ساختنِ انتزاعِ
کامل است.

### ۲) مسیرِ آپلود

`/api/upload/sign` امروز `createSignedUploadUrl` سوپابیس را صدا می‌زند.
برای S3-compatible جایش `presigned PUT` می‌آید. همه‌ی بررسی‌های امنیتی
(نشست، نرخ، پیشوندِ مجاز، مالکیت، نوع، سقفِ حجم) پیش از صدورِ مجوز
انجام می‌شوند و **دست نمی‌خورند**.

بررسیِ پس از آپلود (`PUT` همان مسیر) هم می‌ماند: سرآمدِ فایل را
می‌خواند و جعلی را پاک می‌کند.

### ۳) دیتابیس — بدونِ تغییرِ ساختار

برای ویدیو:
```sql
UPDATE videos SET storage_provider = 'r2' WHERE storage_provider = 'supabase';
```

برای تصویرها — یک بار، به‌ازای هر ستون:
```sql
-- نمونه؛ پیشوندها را از lib/supabase-config.ts بردار
UPDATE clubs SET logo = replace(logo, :old_prefix, :new_prefix)
WHERE logo LIKE :old_prefix || '%';
```
ستون‌هایی که نشانی دارند: `clubs.logo`, `clubs.images`,
`users.avatar`, `tables.photoDataUrl`, `profiles.data` (JSON — با
`jsonb` و `replace` روی متن)، و فهرست‌های JSONِ داخلِ Storage
(`social/media/index.json`, `social/stories/index.json`).

### ۴) فرانت‌اند — بدونِ تغییر

هیچ کامپوننتی نشانی نمی‌سازد؛ همه از پاسخِ API می‌گیرند.

### ۵) نشانی‌های قدیمی

فایل‌ها را **کپی** کن، نه انتقال. باکتِ قدیمی چند ماه بماند تا هر
نشانیِ کش‌شده‌ای (CDN، شبکه‌های اجتماعی، ایمیل) نشکند. بعد پاکش کن.

---

## ترتیبِ اجرا، آن روز

1. باکتِ تازه + کپیِ همه‌ی فایل‌ها (باکتِ قدیمی دست‌نخورده)
2. راستی‌آزمایی: تعداد و اندازه‌ی فایل‌ها در دو طرف یکی باشد
3. افزودنِ ارائه‌دهنده به کد + CSP، بدونِ عوض‌کردنِ `storage_provider`
4. deploy — هنوز همه‌چیز از باکتِ قدیمی خوانده می‌شود
5. `UPDATE` روی چند ردیفِ آزمایشی → بررسیِ چشمی
6. `UPDATE` روی بقیه
7. `UPDATE` روی ستون‌های تصویر
8. چند هفته پایش، بعد حذفِ باکتِ قدیمی

هر مرحله برگشت‌پذیر است تا مرحله‌ی ۸.

## شکافی که مستقل از مهاجرت است

**پشتیبانِ فایل‌ها.** Supabase از دیتابیس پشتیبان می‌گیرد، از Storage
نه. این با مهاجرت حل نمی‌شود — R2 هم خودبه‌خود پشتیبان نمی‌گیرد.

بهترین نقطه‌ی افزودنش: **همان روزِ مهاجرت**، چون فایل‌ها به‌هرحال کپی
می‌شوند و نگه‌داشتنِ باکتِ قدیمی به‌عنوان نسخه‌ی دوم تقریباً رایگان
است. پیش از آن، ساده‌ترین شکل یک کارِ دوره‌ای است که فقط فایل‌های تازه
را جای دیگری هم می‌گذارد.
