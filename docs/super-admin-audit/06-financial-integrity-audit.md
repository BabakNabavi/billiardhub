# یکپارچگی مالی

هیچ پرداخت، بازپرداخت یا تسویه‌ی واقعی یا آزمایشی اجرا نشد. همه‌ی موارد زیر با خواندن کد است.

## عملیات مالی پنل

| عملیات | مسیر | نگهبان (پس از رفع) | منطق |
|---|---|---|---|
| ثبت واریز تسویه به باشگاه | `POST /api/admin/settlements` | `can(finance)` | تابع اتمیک؛ شماره‌ی پیگیری یکدست و ضدتکرار |
| تکمیل بازپرداخت رزرو | `POST /api/admin/refunds` (`complete`) | `can(finance)` | `bh_complete_refund`؛ شماره‌ی پیگیری ضدتکرار؛ `audit` با `REFUND_COMPLETED` |
| تکمیل بازپرداخت تبلیغات | `POST /api/admin/refunds` (`complete-ad`) | `can(finance)` | دو ستون مهاجرت ۰۶۷؛ `audit` با `AD_REFUND_PAID` |
| نرخ کمیسیون (سراسری/باشگاه) | `PUT/DELETE /api/admin/commission` | `can(finance)` | |
| لغو رزرو با بازپرداخت خودکار | `POST /api/bookings/[id]/cancel` | صاحب رزرو، مالک باشگاه، یا `can(bookings)` ⟵ **پیش از رفع: هر ادمین** | محاسبه‌ی متمرکز `computeRefund`؛ اثر اتمیک |
| حساب بانکی باشگاه (ثبت/تأیید) | `POST/PATCH /api/clubs/[id]/bank-account` | مالک یا `can(finance)` ⟵ **پیش از رفع: هر ادمین** | |
| گزارش مالی باشگاه | `GET /api/clubs/[id]/finance` | مالک یا `can(finance)` ⟵ **پیش از رفع: هر ادمین** | |
| سلامت درگاه | `GET /api/admin/payments/health` | `can(finance)` ⟵ **پیش از رفع: هر ادمین** | |
| لغو مسابقه (بازپرداخت ثبت‌نام‌ها) | `DELETE /api/tournaments/[id]` | مالک باشگاه یا `can(tournaments)` ⟵ **پیش از رفع: هر ادمین (D2)** | فقط با `bh_tournament_cancel` |

## رابط

- `PayoutOrders` (`components/admin/PayoutOrders.tsx`): پاسخ را با `r.ok` چک می‌کند، پیام خطای سرور را نشان می‌دهد و پس از موفقیت فهرست را دوباره از سرور می‌خواند.
- اسکریپت ممیزی اول آن را «بی‌چک» نشان داد که هشدار کاذب بود. چک کمی دورتر از فراخوانی است.
- پنجره‌ی شماره‌ی پیگیری پس از هر نتیجه بسته می‌شود. در شکست پیام خطا نشان داده می‌شود.

## یافته‌ها

- **منطق تراکنش و ضدتکرار درست به نظر می‌رسد** (ایستا). در زمان اجرا سنجیده نشد.
- **نقص اصلی مالی، مجوز بود نه محاسبه:** پیش از رفع، هر ادمینی با هر دسترسی می‌توانست:
  - رزرو را با بازپرداخت لغو کند (D1)،
  - حساب بانکی باشگاه را تأیید یا رد کند (D1)،
  - مسابقه را لغو کند و بازپرداخت ثبت‌نام‌ها را راه بیندازد (D2).
- `GET /api/bookings/[id]/cancel` مبلغ و درصد بازپرداخت هر رزرو را بی‌احراز هویت می‌داد (D5).

## سنجیده نشد

- سازگاری دفتر کل با کیف پول و تسویه روی داده‌ی واقعی.
- کالبک درگاه با پرداخت آزمایشی (پی‌پینگ sandbox).
- آزمون `test:finance` (`test-financial-invariants.mjs`)، که روی دیتابیس زنده می‌نویسد.
- کرون تسویه روی سرور (`cron-tick.sh`)، که شرط حیات تسویه است (یادداشت finance-architecture).
