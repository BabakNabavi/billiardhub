# ممیزی امنیتی پنل ادمین

## آنچه با اجرا سنجیده شد

**درخواست مستقیم بی‌نشست به سایت زنده** (`https://billiardhub.net`، کد پیش از رفع)، به همه‌ی مسیرهای `/api/admin/*` و `/api/owner/*`، ۱۶ مسیر مالک باشگاه و چند مسیر دیگری که صفحه‌های ادمین صدا می‌زنند، با هر متدی که صادر می‌کنند. بدنه‌ی ساختگی و شناسه‌ی صفر (`00000000-…`) فرستاده شد.

- ۱۱۳ ترکیب. ۹۹ تا ۴۰۱ یا ۴۰۳ دادند.
- ۱۴ تای دیگر بررسی شدند:
  - ۱۱ تا خواندنی عمومی طبق طراحی‌اند: فهرست باشگاه‌ها، برندها، مسابقه‌ها، استوری‌ها، پخش زنده، و ۴۰۴ برای شناسه‌ی ناموجود.
  - `GET /api/bookings/[id]` بی‌نشست فقط با شماره‌ی پیگیری همان رزرو جواب می‌دهد، که راه بازگشت از درگاه است و درست است.
  - `POST /api/streams/manage` ورودی را پیش از نشست اعتبارسنجی می‌کند، ولی هیچ نوشتنی پیش از نگهبان نیست.
  - **`GET /api/bookings/[id]/cancel` هیچ احراز هویتی نداشت** (D5).

**همان جاروب روی سرور محلی پس از رفع:** ۱۵۰ ترکیب، ۱۲۵ رد، و **هیچ ۵۰۰** (اطمینان از نبود import حلقوی یا خطای زمان اجرا در مسیرهای تغییرکرده).

## آنچه با خواندن کد سنجیده شد

| موضوع | یافته |
|---|---|
| احراز هویت | نشست امضاشده در کوکی، توکن دسترسی ۱۵ دقیقه + تمدید (`lib/auth`). |
| مجوز سرورساید | ۴۱ API که صفحه‌های ادمین صدا می‌زنند همه نگهبان دیتابیسی دارند. **ولی ۲۷ فایل فقط «ادمین بودن» را می‌پرسیدند** (D1) و `ownsClub`/`ownsSeller` هر ادمینی را مالک می‌دانستند (D2). |
| دستکاری نقش از کلاینت | نقش ادمین همیشه از دیتابیس خوانده می‌شود. `actorOf` صریحاً می‌گوید چرا: `primaryRole` را خود کاربر از `PATCH /api/users/me` عوض می‌کند. |
| ارتقای دسترسی بین ادمین‌ها | کلید `access` فقط سوپر است؛ تغییر دسترسی فقط با `isSuperAdmin`. پیش از رفع، D1 و D2 همین مرز را دور می‌زدند. |
| نشست کاربر مسدود | proxy برای هر API وضعیت را از دیتابیس می‌خواند و `actorOf` هم دوباره `canSignIn` می‌کند. `test:enforcement` ۱۰۵ از ۱۰۵. |
| CSRF | Origin + توکن دوگانه (proxy.ts). معافیت‌ها فهرست صریح دارند و هر کالبک درگاه verify سرورساید دارد. |
| ثبت ممیزی | بیشتر عملیات تغییردهنده `audit()` دارند. `audit` خطا را می‌بلعد، پس شکست ثبت عملیات را متوقف نمی‌کند (عمدی). |
| تنظیمات | فهرست سفید کلیدها؛ کلید ناشناخته نوشته نمی‌شود. |

## نقص‌ها (همه رفع شدند — جزئیات در ۰۷)

- **D1 (P1):** ۲۷ مسیر کلید دسترسی صفحه را نادیده می‌گرفتند.
- **D2 (P1):** ادمین همیشه «مالک» هر باشگاه و فروشگاه بود، در ۱۷ فراخوانی.
- **D5 (P3):** پیش‌نمایش بازپرداخت رزرو بی‌احراز هویت بود.

## آنچه عمداً عوض نشد

- `admin/errors`، `admin/logs` و `admin/stats` همچنان «هر ادمین»اند، چون صفحه‌شان کلید دسترسی ندارد. ژورنال رویدادها شامل IP، عامل کاربر و نشست‌هاست. پیشنهاد: کلید تازه یا فقط سوپر، که تصمیم طراحی است.
- `admin/review` و `admin/license-check`: پس از بازبینی، هر دو پس از خواندن ردیف کلید همان نوع را می‌خواهند (باشگاه ⟵ `clubs` یا `roles`؛ پروفایل ⟵ کلید نوع یا `roles`؛ درخواست نقش ⟵ `roles` یا کلید همان نقش). دروازه‌ی اولیه‌ی `REVIEW_KEYS` فقط پیش‌فیلتر است.
- خواندن `admin/settings` برای هر ادمین. محتوایش پیکربندی است، نه داده‌ی شخصی.

## آنچه سنجیده نشد

- آزمون زمان اجرا با نشست کاربر عادی یا ادمین محدود، چون حساب آزمایشی یا راه امن ساخت توکن نبود. جایگزینش آزمون ایستای `test:admin-perms` است.
- IDOR در مسیرهای غیرادمین، XSS، امنیت آپلود و محدودیت نرخ: خارج از دامنه‌ی این ممیزی که پنل ادمین بود. در ممیزی‌های قبلی پروژه بخش‌هایی از آن‌ها پوشش داده شده (`test:guards`، `test:lock`).
