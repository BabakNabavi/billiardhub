# درگاه پرداخت پی‌پینگ

## وضعیت
کد نوشته و آزموده شده، ولی **فعال نیست**. تا وقتی `PAYMENT_PROVIDER`
عوض نشود، سایت همان درگاهِ آزمایشی (`mock`) را به کار می‌برد و هیچ پولِ
واقعی جابه‌جا نمی‌شود.

## روشن‌کردن — دو متغیر در Vercel

```
PAYPING_TOKEN     = <توکن اختصاصی از کنسول توسعه‌دهنده‌ی پی‌پینگ>
PAYMENT_PROVIDER  = payping
```

بعدش **ری‌دیپلوی**. متغیرهای Vercel در لحظه‌ی دیپلوی بسته می‌شوند و
عوض‌کردنشان روی دیپلویِ فعلی اثری ندارد.

### ساختنِ توکن
`app.payping.ir/connections/developers` ← «توکن جدید»

- **آدرس وب‌سایت:** `billiardhub.net`
- **دسترسی‌ها:** فقط **«ساخت پرداخت»** و **«گزارش پرداخت‌ها»**.
  تأییدِ نهایی هم زیرِ «ساخت پرداخت» است و اجازه‌ی جدا ندارد.
  بقیه (کد تخفیف، مشتری، فاکتور، محصول، اقساطی، آپلود) به کار
  نمی‌آیند. «شارژ حساب ریفاند» عمداً گرفته نشده — سنگین‌ترین دسترسیِ
  فهرست است و بازگشتِ خودکار در عمل استفاده نمی‌شود.
- توکن **فقط یک‌بار** نشان داده می‌شود.

### برگرداندن
`PAYMENT_PROVIDER` را به `mock` برگردانید و ری‌دیپلوی کنید. کدِ
پی‌پینگ سرِ جایش می‌ماند و کاری نمی‌کند.

## آنچه از مستنداتشان درآمد

| | |
|---|---|
| پایه | `https://api.payping.ir` |
| احراز | `Authorization: Bearer <توکن>` |
| **واحد پول** | **تومان** |
| ساخت پرداخت | `POST /v3/pay` → `{ paymentCode, url }` |
| تأیید | `POST /v3/pay/verify` با `paymentRefId` + `paymentCode` + `amount` |
| بازگشت وجه | `POST /v3/pay/reverse` — فقط تا **۳۰ دقیقه** پس از تأیید |

### واحد پول — مهم‌ترین تفاوت با زرین‌پال
زرین‌پال **ریال** می‌گیرد و آداپتورش ضربدر ده می‌کند. پی‌پینگ **تومان**
می‌گیرد، دقیقاً مثل خودِ سیستم، پس هیچ تبدیلی در کار نیست. یک ضربدرِ ده
اشتباهی این‌جا یعنی ده برابر گرفتن از مشتری.

### بازگشت از درگاه — تفاوتی که کد را عوض کرد
درگاه‌های دیگر با `GET` و پارامترِ کوئری برمی‌گردند. پی‌پینگ به
`returnUrl` یک **`POST` با `application/x-www-form-urlencoded`** می‌زند:

```
status     = 1 موفق · 0 ناموفق
errorCode  = کد خطا (در موفق خالی)
data       = JSON: { clientRefId, paymentCode, paymentRefId,
                     amount, gatewayAmount, cardNumber, cardHashPan }
```

هر شش مسیرِ بازگشتِ سایت (رزرو، مسابقه، تبلیغ، بسته‌ی آگهی، بسته‌ی
استوری، پیامکِ باشگاه) حالا از `lib/payments/return.ts` می‌خوانند که
هر دو شکل را می‌فهمد.

`clientRefId` را هنگام ساخت برابرِ شناسه‌ی سفارشِ خودمان می‌فرستیم —
همان‌طور که مستنداتشان می‌گوید. اگر روزی پارامترِ کوئریِ `returnUrl` گم
شود، باز هم می‌دانیم کدام سفارش است.

### پاسخ‌های تأیید که خطا نیستند
- **۴۰۹ با `metaData.code = 110`** — قبلاً تأیید شده. پول گرفته شده؛
  کالبکِ تکراری نباید سفارش را ناموفق کند.
- **۲۰۲ و ۵۰۲** — در حالِ پردازش. نه تأیید است نه رد؛ سفارش «ناموفق»
  علامت نمی‌خورد تا بشود دوباره امتحان کرد.

### بازگشت وجه
`POST /v3/pay/reverse` فقط **۳۰ دقیقه** پس از تأیید کار می‌کند، و
پرداخت باید با `isReversible: true` ساخته شده باشد.

این پیش‌فرض **خاموش** است (`PAYPING_REVERSIBLE=on` روشنش می‌کند) چون
رفتارِ تسویه را عوض می‌کند و باید آگاهانه انتخاب شود. در عمل، لغوِ رزرو
معمولاً روزها بعد است، پس بازگشتِ خودکار فقط برای لغوِ بلافاصله به کار
می‌آید؛ بقیه دستی می‌مانند — همان وضع امروز.

## سلامتِ درگاه — وقتی شک کردید

با حسابِ ادمین این را باز کنید:

```
/api/admin/payments/health?probe=1
```

یک دستورِ پرداختِ کوچک می‌سازد و بی‌درنگ حذفش می‌کند. **هیچ پولی
جابه‌جا نمی‌شود** چون کسی به صفحه‌ی درگاه نمی‌رود، ولی توکن، دسترسی‌ها
و اتصال هر سه با هم سنجیده می‌شوند.

بدونِ `?probe=1` فقط تنظیمات را گزارش می‌کند و هیچ درخواستی بیرون
نمی‌رود:

```json
{ "selected": "payping", "active": "payping",
  "realGateway": true, "tokenSet": true }
```

اگر `selected` و `active` یکی نبودند، یعنی درگاهِ انتخابی پیکربندی
نشده و سیستم به `mock` برگشته — همان حالتی که «پرداخت موفق» نشان
می‌دهد بدونِ آنکه ریالی جابه‌جا شده باشد.

اولین جایی که پس از انقضای توکن باید سر بزنید همین است.

## آزمون
```
node apps/web/scripts/test-gateway-return.mjs
```
خواندنِ بازگشت را در هفت حالت می‌سنجد: کوئریِ زرین‌پال، فرمِ پی‌پینگ،
لغو، بدنه‌ی خالی، `data`ی خراب و بدنه‌ی JSON. بدونِ شبکه و دیتابیس
اجرا می‌شود.

اگر این تابع یکی از دو شکل را نفهمد، نتیجه‌اش **پولِ گرفته‌شده و
سفارشِ فعال‌نشده** است — و در آزمونِ دستی هم دیده نمی‌شود، چون فقط با
پرداختِ واقعی رخ می‌دهد.

## پس از روشن‌کردن، اولین آزمون
یک رزرو با کمترین مبلغِ ممکن بگیرید و تا آخر ببرید. بررسی کنید:

۱. به درگاهِ پی‌پینگ می‌روید (نه صفحه‌ی mock)
۲. بعد از پرداخت به `/booking/result` برمی‌گردید با نتیجه‌ی موفق
۳. در پنل ادمین، رزرو `PAID` است
۴. در پنل پی‌پینگ همان مبلغ دیده می‌شود
۵. پیامکِ «رزرو قطعی» می‌رسد

اگر ۲ درست بود ولی ۳ نه، مشکل در تأیید است نه در پرداخت — لاگِ Vercel
را ببینید.
